# Проверка согласованности стандартов и скиллов

Одни и те же факты записаны в нескольких местах (форматы тегов и веток, поля статуса, колонки карты, значения словарей), и со временем они расходятся. Ты читаешь файлы и составляешь отчёт о расхождениях. **Ничего не правь**, пока пользователь не попросил: исправление — отдельное действие.

## Где лежат скиллы

Папка скиллов — **родительская папка той, где лежит этот `SKILL.md`**. Путь к самому скиллу виден при его запуске («Base directory for this skill: …/skills/standards-audit»), значит остальные скиллы лежат в `…/skills/`. В плагине `armarium` это папка `skills/` плагина, а пока плагин не включён и работают оригиналы — `~/.claude/skills`. Не определил путь — спроси пользователя, не угадывай. Если одновременно существуют и плагин, и оригиналы в `~/.claude/skills`, сверь их между собой (`diff -rq`, служебную папку `synced` не считай): расхождение между ними — отдельная находка, источник истины — плагин.

Стандарты лежат в `<vault>/Проекты` хранилища Obsidian; корень хранилища `<vault>` берётся из настроек (`~/.claude/armarium.json`, подробности в `../../docs/settings.md` от папки этого скилла). Скиллы плагина ссылаются на путь через `<vault>`, жёстко прописанных путей вашей машины в них быть не должно: это отдельная проверка.

## Что проверять

Сначала ищи конкретные факты через `grep`, а не читай файлы целиком: так дешевле и точнее. Читай целиком только то место, где нашлось расхождение.

| Что | Где сверять |
| --- | --- |
| Теги ПО `g<N>-v<версия>`, ветки `gen-N` | `Стандарт по названию проектов.md`; скиллы `release-versioning`, `firmware-esp-stm`, `project-scaffold`, `naming-standards` |
| Теги устройств `g<N>-<часть>-<ревизия>`, ревизии `r…`, `v…` | `Стандарт по названию устройств.md`; `hw-board-check`, `release-versioning` |
| Поля заметки `Статус` | раздел «Заметки Проекта» в `Стандарт проектных заметок.md`; `project-stages/assets/status.md`; текст `project-stages/SKILL.md` |
| Колонки и формат строки `Карта проектов` | `Стандарт проектных заметок.md`; `project-stages/assets/karta-proektov.md`; `Проекты/Карта проектов.md` |
| Значения словарей: платформы, UI, типы, виды | `Стандарт по названию проектов.md`, `Стандарт по названию устройств.md`; таблица групп в `Стандарт проектных заметок.md` |
| Разделы заметок (Идея, Требования, Архитектура, План, Решения, Вопросы) | `Стандарт проектных заметок.md`; шаблоны в `project-stages/assets/` и `test-plan/assets/` |
| Имена заметок `<кодовое слово> - <Тип заметки>` | стандарт заметок; шаблоны; скиллы |
| Правила режима наставника (кто пишет код, примеры 1–3 строки) | `project-scaffold`, `release-versioning`, `firmware-esp-stm`, `code-coach`, `project-stages`, `test-plan` — не противоречат ли друг другу и стандарту |
| Пути и перекрёстные ссылки | существуют ли файлы и скиллы, на которые ссылаются |
| Таблицы «Открытые пункты» и даты решений | статусы в таблице соответствуют тексту разделов |

## Как отвечать

Отчёт — таблицей: **что проверял · где · результат**. Результат — одно из трёх: `согласовано`, `расхождение` (с цитатой и местом, файл и строка), `не проверено` (и почему). Расхождения перечисли в порядке важности: сначала те, из-за которых скилл сделает неправильно (формат тега, поля статуса), потом косметика. Для каждого расхождения предложи, **какой файл считать источником истины** и что поправить, но не правь, не спросив. Ничего не придумывай: если не можешь проверить, так и скажи.

Если пользователь попросил исправить: правь только то, о чём он сказал «да», и после правок перепроверь затронутые пункты.

## Границы

- Только чтение; исключение — правка по прямому «исправь» пользователя.
- Существующие проекты в хранилище не проверяются (пользователь считает их устаревшими по структуре и правилам).
- Если стандарт и скилл расходятся и неясно, что верно, не выбирай сам: спроси пользователя.
