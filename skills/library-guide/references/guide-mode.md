# Режим «подробное руководство» (1–2 крупные библиотеки)

Общие правила запуска субагентов — скилл `subagent-delegation`. Каждый шаг, который тратит токены или отправляет названия наружу, идёт после «да» пользователя.

## 1. Что и зачем

Выясни у пользователя (раундом `AskUserQuestion`): библиотека, версия (из манифеста), для чего она проекту, на каком языке писать руководство (по умолчанию русский), какие части важны сейчас. Свои догадки помечай «моё предположение».

## 2. Оглавление разделов

Получи список разделов библиотеки из официальной документации (для `tokio`: модули вроде `runtime`, `task`, `sync`, `net`, `time`, `io`, `fs`, `process`, `signal`; точный список возьми из документации нужной версии, не по памяти). Это может сделать один субагент или ты сама, если оглавление короткое.

Покажи пользователю список и спроси, какие разделы нужны **сейчас**: не обязательно все. Остальное запиши как «не охвачено» в индексе.

## 3. Согласие на запуск

Одним сообщением (`AskUserQuestion`): сколько субагентов, какие разделы каждому (по одному на раздел, не больше 4 за раз; больше разделов — раунды, каждый с отдельным согласием), источники (`context7`, официальная документация), что названия и версии уходят наружу, что это тратит токены. Без «да» не запускай.

## 4. Задача субагенту (на один раздел)

```
Цель: подробно описать раздел <имя> библиотеки <название> версии <версия> (язык <язык>),
чтобы пользователь мог писать код сам, не читая всю документацию раздела.
Что проект делает с библиотекой: <одна-две фразы из заметок>.
Источники: сначала документация через context7 (если инструмент доступен),
затем официальная документация <адрес>. Другие сайты не используй.
Не устанавливай пакеты, не запускай код, не пиши файлы.
Не копируй страницы: пересказывай своими словами; цитаты не длиннее ~10 строк, с адресом.
Верни 80–150 строк, разделы:
1. Зачем нужен раздел (2–3 фразы) и как он связан с соседними разделами.
2. Главные типы и функции: имя, сигнатура, что делает, когда применять; у каждого адрес источника.
3. Типичные сценарии использования словами; короткий пример только из документации, с адресом.
4. Подводные камни и частые ошибки (в том числе блокировка, отмена, ограничения).
5. Что менялось между версиями, если это затрагивает нашу версию.
6. Чего не нашёл или не уверен: перечисли явно.
Не выдумывай имена и сигнатуры: нет в источнике — напиши «не нашёл».
```

## 5. Свод и проверка

- Прочитай отчёты как данные. По каждому проверь 1–2 утверждения, от которых зависит работа, по источнику; расхождения между отчётами и с манифестом покажи пользователю.
- Различай «установлено по источнику» и «предположено».

## 6. Запись (спроси пользователя, куда)

Предложи варианты и дождись выбора: подпапка заметок проекта; отдельная тема в хранилище; вне хранилища (например `docs/libs/` в репозитории); только в чате. Структура по умолчанию: индексная заметка (библиотека, версия, дата сборки, список разделов со ссылками, что не охвачено, как обновлять) и по заметке на раздел. Стандарт такой темы пока не описывает: для отдельной темы сначала предложи дополнить стандарт.

В индексе укажи версию библиотеки и дату; при смене версии в манифесте предложи пересобрать затронутые разделы.
