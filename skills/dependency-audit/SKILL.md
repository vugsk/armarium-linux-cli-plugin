# Проверка зависимостей на уязвимости и ошибки

Ты проверяешь зависимости и сообщаешь, что нашлось. **Выбор делает пользователь, а проблемы в выбранной зависимости исправляет он сам:** ты описываешь, где и почему они возникают, а способ исправления даёшь только по его просьбе. Лицензии зависимостей — отдельная проверка (`repo-init`, справка `licenses.md`). Безопасность кода самого проекта — скилл `project-security`.

Заметки проекта лежат в `<vault>/Проекты/<кодовое слово>/`: `<vault>` — корень хранилища из `~/.claude/armarium.json`; прочитай `../../docs/settings.md` (путь от папки этого скилла) и следуй ему, не угадывай путь и не подставляй путь своей машины.

## Источники и честность данных

Бери сведения только из источников, по сети и только для чтения; каждое утверждение — со ссылкой. Что не удалось найти, помечай «не проверено», а не «безопасно»: отсутствие записи в базе не доказывает отсутствие уязвимости.

- **Базы уязвимостей:** OSV (osv.dev), GitHub Advisory Database, базы экосистем (RustSec, advisory-записи PyPI, база уязвимостей Go на pkg.go.dev/vuln), NVD для CVE. Тяжесть бери из самой записи (оценка CVSS и метка critical, high, medium, low) и укажи, откуда она.
- **Состояние проекта библиотеки:** дата последнего релиза, помечена ли как заброшенная (archived, deprecated, unmaintained), есть ли сведения об обновлениях безопасности, открытые заявки с пометками о критических ошибках. Только по реестру пакетов и репозиторию библиотеки.
- **Дополнительно по просьбе пользователя:** запуск установленных инструментов (например, аудит зависимостей экосистемы, статический анализ, собственные тесты библиотеки). Проверь по документации, какие инструменты есть и как они вызываются, прежде чем называть команды; ничего не устанавливай без согласия.

## Порядок работы

1. Выясни (раундами по 1–4 вопроса: после каждого раунда анализируй ответы и спрашивай дальше только нужное; заверши, когда ясно или пользователь написал «хватит»; подробнее: «Раунды Вопросов» в стандарте проектных заметок): экосистему и язык, кандидатов на зависимость или путь к манифесту проекта, версию (или диапазон), как зависимость будет использоваться (что именно из неё нужно: от этого зависит, затрагивает ли проблема проект).
2. **Собери данные** по каждому кандидату и версии (включая транзитивные зависимости, если речь о проверке существующих).
3. **Ранжируй от самого проблемного к наименее проблемному**, критические проблемы первыми. Таблица: зависимость · версия · проблемы по тяжести (с идентификаторами) · исправлены ли и в какой версии · состояние проекта · источник · не проверено.
4. **Рекомендуй наименее проблемный вариант** и объясни компромиссы (например, меньше проблем, но реже обновляется; больше возможностей, но есть критическая запись). В тексте рекомендации (а не в таблице, где порядок задан тяжестью проблем) начинай с варианта, который считаешь лучшим. Применимость проблемы к использованию пользователя оценивай вместе с ним: из базы это не следует.
5. **Выбор за пользователем.** Если вариантов без проблем нет и он берёт зависимость с проблемами, составь по ней разбор по шаблону `assets/dependency-report.md`: для каждой проблемы идентификатор, тяжесть, затронутые версии, **где возникает** (компонент или функция по записи), **почему** (причина по записи), **как проявляется**, статус исправления по записи (в какой версии исправлено, если исправлено). Способ исправления или обхода — только по его запросу.
6. **Запись.** Разбор и итоговая таблица — заметка `<кодовое слово> - Зависимости` (в папке `Проверки/` проекта, если она есть). Выбор зависимости и принятые риски — в заметку `Решения`, только после явного решения пользователя.

## Границы

- Не меняй манифесты, lock-файлы и версии зависимостей, не устанавливай и не обновляй пакеты: это его действия.
- Не запускай код зависимостей из непроверенных источников; запуск инструментов и тестов библиотеки только по просьбе и в изолированной папке.
- Не выдавай за факт то, чего нет в источнике. Данные баз могут быть неполными; об этом говори в отчёте.
- Не принимай решение за пользователя: ни «берём эту», ни «риск допустим».
