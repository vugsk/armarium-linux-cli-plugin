# Отладка

Режим наставника: объясняй метод и называй инструмент; находит и исправляет пользователь.

**Метод (одинаков для любого языка):** воспроизвести сбой стабильно → сузить место (бинарный поиск по коду, минимальный пример) → сформулировать гипотезу → проверить её **одним** изменением или наблюдением → исправить → добавить проверку, чтобы сбой не вернулся. Не менять несколько вещей сразу: иначе неясно, что помогло.

**Наблюдать можно тремя способами:** журнал (вывод в нужных местах), отладчик (остановка и осмотр состояния), автоматические проверки (санитайзеры, анализаторы). Начинай с самого дешёвого.

**Инструменты по языкам** (названия верны, **флаги и команды проверь в документации своей версии**):
- **Rust:** переменная окружения `RUST_BACKTRACE=1` для стека при панике, макрос `dbg!`, `rust-gdb` и `rust-lldb`, `cargo test` для воспроизведения тестом.
- **C и C++:** gdb или lldb; санитайзеры компилятора (AddressSanitizer, UBSan, включаются флагами `-fsanitize=…`); valgrind; предупреждения компилятора (`-Wall -Wextra`).
- **Python:** `breakpoint()` и `pdb`, модуль `logging`, `traceback`.
- **Go:** отладчик delve (`dlv`), `go vet`, проверка гонок флагом `-race` у `go run`/`go test`.
- **Java:** отладчик IDE или `jdb`, трассировка стека.
- **NASM и ARM-ассемблер:** gdb в режиме по инструкциям (`stepi`), просмотр регистров и памяти.

**Прошивки (ESP, STM):** сначала проверь основы: питание, такты, подключение выводов, общая земля. Дальше: журнал через UART, логический анализатор или осциллограф для сигналов, отладчик через SWD и OpenOCD, разбор аппаратного сбоя (hard fault) по регистрам и стеку. Конкретные регистры и номера — по Reference Manual своего МК. Периферия — скилл `firmware-esp-stm`.

**Типичные ловушки:** отладка не той версии кода (старая сборка), «работает у меня» из-за неопределённого поведения, ошибка в самом тесте, ошибка окружения.

**Примеры на другой задаче:** показывай приём (например, как сузить место ошибки) на игрушечном коде, а не на коде его проекта.
