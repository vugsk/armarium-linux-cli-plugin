# Готовность к релизу

Правила этапов — в `<vault>/Проекты/Стандарт проектных заметок.md` (таблица этапов, критерии выхода этапа 7 и входа в этап 8, раздел «Особенности Групп»). Пути берутся из настроек: прочитай `../../docs/settings.md` и следуй ему; `<vault>` — корень хранилища.

Скилл **читает и сверяет**, ничего не меняет и не запускает проверки сам. Закрывает этап и решает о выпуске только пользователь.

## Что сверяешь

Если в `Статус` есть поле `Нумерация этапов: старая (6 этапов)`, читай номера этапов по старой таблице стандарта (проверка — этап 4, релиз — этап 5). Прочитай `Статус`, `Проверки`, `Безопасность`, `Зависимости`, `Релиз` проекта и, если нужно, репозиторий (путь спроси). По каждому пункту дай статус **есть / нет / устарело / не проверено** и источник (заметка, файл, дата):

1. **Тесты:** заметка `Проверки`, все тесты запущены, результаты записаны, критерии выхода этапа 7 сверены; результаты не старее последних изменений кода (сравни даты с историей репозитория).
2. **Безопасность:** заметка `Безопасность` есть, найденные пункты закрыты или приняты пользователем явно.
3. **Зависимости:** если у проекта есть зависимости, заметка `Зависимости` есть, критические проблемы закрыты или приняты.
4. **Лицензия и README:** `LICENSE` совместима с лицензиями зависимостей, README наполнен (не скелет).
5. **Версия и теги:** версия в сборке, тег и changelog соответствуют стандарту; рабочее дерево чистое.
6. **Заметка `Релиз`:** чек-лист, формат поставки, текст релиза, описание для каталога при публикации; публичное имя выбрано.
7. **Особенности типа проекта:** для устройства — `hw-board-check` и паспорт изделия; для библиотеки — документация и примеры; для игры — играбельность и производительность.
8. **Открытые вопросы:** в `Вопросы` нет блокирующих.

## Вердикт

Таблица пунктов и итог: **готов** (всё «есть») или **не готов** (перечисли, чего не хватает). Для каждого пробела назови скилл, который его закрывает: `test-plan`, `project-security`, `dependency-audit`, `repo-init`, `release-versioning`, `project-stages`. Состояние «не проверено» — не «есть»: так и пиши.

## Внешние помощники (если установлены)

Плагин `github` (официальный GitHub MCP) позволяет прочитать то, чего нет в заметках: статус CI последнего коммита, открытые заявки и pull request, теги и релизы в репозитории. Установлен он или нет, определи по списку доступных инструментов сессии (инструменты с `github` в имени); имена не придумывай. Нужен токен `GITHUB_PERSONAL_ACCESS_TOKEN`, заводит пользователь; при ошибке токена пункт остаётся «не проверено».

- **Только чтение:** используй его для пунктов 5 (тег и релиз существуют на удалённом репозитории) и 8 (блокирующие заявки). Не создавай заявки, pull request, релизы и теги, не комментируй и не закрывай: это действия пользователя.
- Данные укажи с источником («GitHub, репозиторий, дата») и отдели от того, что взято из заметок; расхождение между заметкой и GitHub — отдельная строка отчёта.
- Репозиторий называет пользователь; чужие репозитории не читай.

## Границы

- Ничего не правь, не коммить, не ставь теги, не запускай тесты и аудиты: только читай и отчитывайся. Если заметка устарела, скажи и предложи перезапустить нужный скилл.
- Не придумывай факты о состоянии проекта: чего нет в заметках и репозитории, то «не проверено». Не помечай решение «принято» за пользователя.
- Переход на этап 8 делает `project-stages` после явного «переходим» пользователя.
