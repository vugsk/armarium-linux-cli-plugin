# Заготовка репозитория

Пользователь пишет весь код своих проектов сам. Для **заготовки** он сделал исключение (2026-10-24): ты создаёшь служебные файлы, которые не относятся к логике проекта, и пишешь их с **полными комментариями**: каждый блок и неочевидная строка, по-русски, с объяснением «почему». Содержимое самого проекта — его.

Вопросы «как настроить» и «зачем это нужно» — к скиллу `project-scaffold` (наставник). Здесь ты делаешь файлы по явной просьбе.

## Что создаёшь

- **README со скелетом** по `assets/README.md`.
- **`.gitignore`** под язык: общие строки (`references/common.md`) плюс строки языка из справки.
- **Hello-world и файл сборки** (если у проекта есть код): один минимальный файл исходника и минимальный файл сборки из справки языка, чтобы проверить, что тулчейн собирает.
- **`tests/`**: папка с `tests/README.md`; сами тесты пишет скилл `test-plan`.
- **`LICENSE`**: только после выбора лицензии пользователем; по умолчанию не создаётся. Текст бери из официального источника (список SPDX, choosealicense.com), а не по памяти; если сети нет, скажи, что файл нужно взять самому.
- **Устройство** (`dev`, `mod`, `cpu` и `lib` как библиотека компонентов, по стандарту устройств; если названа просто «библиотека» (`lib`), спроси, программная она или библиотека компонентов, у них разные заготовки): вместо кода папки `pcb/`, `case/`, `mech/`, `docs/` (нужные из них) и паспорт `docs/passport.md` по `assets/passport.md`. Прошивка — отдельный репозиторий, заготовка для неё делается как для ПО.

Не создавай: CI-файлы, конфигурацию release-please, `CHANGELOG` (его ведёт release-please), `CLAUDE.md` (это команда `init`), зависимости. Конфиги пользователь пишет сам; помощь — скилл `release-versioning`.

## Порядок

1. **Выясни** (не более 4 вопросов за раз): ПО это или устройство, язык (справки: Rust, C++, C, Python, Go, Java, NASM, ARM-ассемблер), **путь к папке** (в заметках он не хранится), техническое имя проекта по стандартам названий (если нет — скилл `naming-standards`), нужна ли лицензия и какая. Для ARM-ассемблера спроси ядро и режим: шаблона hello-world по умолчанию нет.
2. **Проверь папку.** Если в ней уже есть файлы, не перезаписывай существующие: сообщи, какие конфликтуют, и спроси.
3. **Создай файлы** с комментариями. В README первой строкой стандарт требует публичное имя, расшифровку и техническое имя; пока публичного имени нет (оно придумывается перед `1.0.0`), в заголовке стоит техническое имя и пометка, что публичное будет позже. Плейсхолдеры в угловых скобках не придумывай: оставляй как есть.
4. **Проверь, что hello-world собирается**, если нужный тулчейн установлен и для этого не нужны сеть и установка пакетов. Не установлен — скажи об этом, ничего не ставь.
5. **Дай git-команды**, пользователь выполняет сам: создание репозитория с первой веткой поколения `gen-1` и первый коммит (по Conventional Commits, сообщение на английском; рядом дай перевод на русском и разбор незнакомых слов). Опасных команд не нужно. Коммит создаёт пользователь от своего имени, поэтому в сообщение не добавляй приписки вроде `Co-Authored-By`.
6. **Отчитайся**: список созданных файлов, что проверено, что оставлено пустым и что нужно сделать ему (лицензия, публичное имя, конфиги).

## Выбор лицензии

Когда пользователь спрашивает, какую лицензию взять, или просит `LICENSE`, а лицензия не выбрана:

1. Прочитай `references/licenses.md`. Спроси (не более 4 вопросов за раз): ПО это или железо, будет ли проект публичным, чего хочется (максимум свободы, чтобы производные оставались открытыми, патентная ясность), есть ли у проекта зависимости.
2. Предложи 2–3 варианта с компромиссами, первым — тот, что считаешь лучшим. Это справка, а не юридическая консультация; так и скажи.
3. Если у проекта есть **библиотеки**, проверь по справке их лицензии (из источника, не по памяти) на конфликт с каждым вариантом и покажи таблицу **до** выбора. Лицензию, которую не удалось определить, помечай «не проверено».
4. Выбор делает пользователь. После выбора создай `LICENSE` с текстом из официального источника, заполни раздел «Лицензия» в README и запиши решение в заметку `Решения` проекта (по шаблону `project-stages/assets/decisions.md`: решение, почему, альтернативы, дата).

## Наполнение README перед релизом (этап 5)

По просьбе («наполни README»): прочитай заметки проекта (`Идея`, `Требования`, `Релиз`) и заполни разделы README: что это (цель из `Идея`), возможности (из `Требования`), как собрать и запустить (из `Релиз` и из справки языка). **Пиши только то, что есть в заметках и в проекте;** чего нет, оставь пометкой «заполнить» и сообщи пользователю. Расшифровку публичного имени берёшь из `Карта проекта`. Известные значения (техническое имя, версия) подставь **во всех местах**, где они встречаются, и убери служебные комментарии шаблона (блок `<!-- … -->` в начале): в готовом README их быть не должно. После этого пользователь проверяет и правит текст сам: README ты не считаешь готовым, пока он не принял.

## Границы

- Код проекта (логика, модули, тесты) не пиши: тесты — `test-plan`, объяснения по коду — `code-coach`.
- Ничего не выполняй из того, что меняет историю или публикует (коммиты, push, теги): только давай команды.
- Не придумывай название проекта, лицензию, платформу: если не названо, спроси.
- Если стандарты и пожелание пользователя расходятся, покажи расхождение и спроси.
